## D. Findings

### F-01 - FIXED / VERIFIED: Live confirmation dismissal loses keyboard return focus

**Affected case:** KEY-09. Reproduced after both ordinary opening and a keyboard-only opening sequence in the isolated guard-true API context.

**Steps to reproduce:**

1. Sign in as ACCOUNTANT and use the local API with Live authorization enabled.
2. Select Live Mode, focus Save changes, and activate it with Enter.
3. Confirm that focus enters the modal and Tab remains contained there.
4. Press Escape to dismiss it.
5. Press Tab again.

**Expected:** Dismissal returns focus to Save changes (the invoking action), preserving the keyboard user's position.

**Original actual:** After dismissal, `document.activeElement` is `BODY`. The following Tab focuses the Erve dashboard link at the beginning of the page. Settings/version remain unchanged; this is an accessibility/navigation defect, not unauthorized activation or data loss.

**Relevant components:** `apps/web/src/pages/gst-compliance/GstComplianceSettingsPage.tsx:157` (controlled ConfirmDialog usage), `packages/app-components/src/components/confirm-dialog.tsx` (shared dialog wrapper), and the underlying DialogContent focus lifecycle. The page opens the controlled dialog programmatically without an explicit trigger/return-focus reference. Scope beyond this page was not established.

**Evidence:** [Keyboard-only reproduction data](<C:/Users/kalay/.codex/artifacts/gst-phase1a-browser-qa-20261020/dialog-focus-results.json>), [dismissed state screenshot](<C:/Users/kalay/.codex/artifacts/gst-phase1a-browser-qa-20261020/dialog-dismissal-focus-lost.png>), [actual viewport confirmation screenshot](<C:/Users/kalay/.codex/artifacts/gst-phase1a-browser-qa-20261020/live-confirmation-viewport.png>). The JSON records BODY after Escape and the dashboard link on the next Tab; a static screenshot alone cannot demonstrate the missing focus.

**Correction and root cause:** Radix modal DialogContent prevents its FocusScope fallback restoration and focuses its registered DialogTrigger on close. ConfirmDialog is a controlled, programmatically opened wrapper with no trigger, so that target is absent. This is a reusable wrapper limitation for triggerless consumers, demonstrated here on the GST page; other consumers were not individually browser-tested. ConfirmDialog now forwards the optional Radix `onCloseAutoFocus` callback, without changing its default behavior. Only the GST page opts in, returning focus through a Save button ref when it is connected and enabled. No timer or DOM query was added to application code. A successful version update remounts SettingsEditor and clears its old ref, so the close callback cannot focus the replacement or detached Save button.

**Fix verification (20 October 2026, Asia/Calcutta):** Branch `fix/gst-live-confirmation-focus-f01` in the existing isolated QA worktree, based on freshly fetched `origin/main` at `42e7f24`. Before the fix, Chromium reproduced BODY after Escape and the new Escape/Cancel regression tests both failed with BODY instead of Save. After the fix:
