# DEMO-014 implementation plan

**Goal:** Maintain Distributor-owned Retail Stores and select them in Dispatch Orders while preserving historical destination snapshots and inline form context.

**Authority:** The supplied DEMO-014 brief is the specification and authorizes end-to-end implementation, focused verification, commit and push. No PR or merge; cleanup waits for explicit merge confirmation.

**Architecture:** Extend the existing master-data APIs and components. Keep SaleOrderDistributor and destination identity unchanged. Add a nullable Store reference and code snapshot; copy every existing destination field on selection. Existing destination values remain authoritative on ordinary edits. Backend resolves new selections transactionally and rejects cross-owner or inactive selections.

**Tech stack:** PostgreSQL, Prisma 7, Express, Zod, React, TanStack Query, ERVE design system, Vitest/Supertest.

## Audit findings

- Distributor management is ADMIN/MERCHANDISER; master browsing also permits SENIOR_MANAGEMENT. Reuse these roles for Stores, including inline creation.
- SaleOrderDestination already snapshots label, addressLine1/2, city, state, country, postalCode, GSTIN and contact name/email/phone. Store name maps to label; Store code gets its own column.
- FactoryPackingCarton has exactly one destination. Factory Packing and Packing Audit read the destination record, never the Store. Erve Packing List copies that destination and groups by normalized address plus Distributor; Erve Dispatch and PDFs consume those snapshots. Preserve that consolidation rule.
- Dispatch Order updates use version checks, idempotency, advisory locks, packed-floor validation, carton audit invalidation and a READY_FOR_ERVE/ErveDispatch immutability boundary. Store resolution belongs inside those transactions.
- DistributorLookupField/useServerLookup, FormGrid/FormSection, Dialog and useCursorList supply the required UI patterns.
- Legacy destinations must remain nullable and must never be matched to Stores by text. No DELETE endpoint is necessary; FK RESTRICT protects referenced Stores.

## Review focus

- Unchanged inactive Store references must survive order edits without recapturing changed master data.
- Moving a destination to another Distributor cannot retain a Store owned by the former Distributor.
- Inline modal submit must never bubble into the parent order submit.
- A Store status/edit race must serialize with snapshot creation.
- Identical Store names/codes under different Distributors must retain distinct destination ownership.

Full API/Web regressions run only in existing PR CI. No production/development database migration during local tests.
